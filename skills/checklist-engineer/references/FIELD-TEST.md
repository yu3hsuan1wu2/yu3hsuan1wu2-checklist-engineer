# Field-test branch

A checklist draft is a hypothesis about real work.

Test it where the work actually happens, or in the closest safe simulation available.

## Test one learning question at a time

Examples:

- Is the pause point timed correctly?
- Is one item ambiguous?
- Does the list take too long?
- Does the communication check surface new information?
- Do users shortcut a section?
- Does the list catch the target failure?

Avoid changing five unrelated things in one test round.

## Minimum observation log

For each run record:

- context/case;
- checklist version;
- pause point;
- completion time;
- skipped or shortcut items;
- item confusion;
- catches / near misses;
- unexpected workflow interference;
- communication effect;
- user comment;
- outcome relevant to the target failure.

## Revision rules

Prefer:
1. delete;
2. move to a better pause point;
3. rewrite more exactly;
4. split only when a genuinely different pause point exists;
5. add an item only when evidence supports the added attention cost.

Do not solve every complaint by adding text.

## Stabilization

Treat the checklist as stable only when:

- users can invoke it at the intended pause point without prompting;
- wording is consistently interpreted;
- shortcuts are uncommon;
- completion fits the real work window;
- the target failures/catches can be observed or tracked;
- communication checks produce the intended exchange;
- users still retain necessary professional judgment.

A stable checklist can still evolve when new failure evidence appears.
