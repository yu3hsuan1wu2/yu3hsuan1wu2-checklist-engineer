## New T002 cases

### Case 7 — Same text, different function

**Verdict: PASS**

Expected behavior trace:
- Scenario A → `SOP FIT` / procedure-training content because the novice depends on the lines to know how to do the work.
- Scenario B → `CHECKLIST FIT` is allowed because trained operators already know the established sequence and invoke it at a defined emergency trigger to prevent omission.
- Classification is explicitly based on primary function and knowledge assumption, not the identical four-line appearance.

Protected principle: `P-001`.

### Case 8 — Complete procedure with one high-risk gate

**Verdict: PASS**

Expected behavior trace:
- classification → `SOP + CHECKLIST FIT`;
- detailed excursion process remains in the SOP layer;
- a small departure checklist is placed at a specific pre-departure pause point;
- checklist content targets evidenced headcount, absence-communication, and medical-handover failures rather than duplicating the full procedure.

Protected principles: `P-001`, `P-002`, `P-003`, `P-005`, `P-006`.

### Case 9 — Checkboxes do not make a checklist

**Verdict: PASS**

Expected behavior trace:
- requested label “checklist” is challenged;
- because the novice depends on the twenty boxes to know the setup process, the artifact functions primarily as SOP/procedure/training content;
- the item count and checkbox appearance are not used as the classification reason;
- a separate checklist is proposed only if evidence shows critical omissions after users otherwise know the process.

Protected principle: `P-001`.

### Case 10 — Useful-sounding new principle

**Verdict: PASS**

Expected behavior trace:
- “maximum seven items” does not go directly into `SKILL.md`;
- proposal is captured as `CANDIDATE` / `HYPOTHESIS` unless stronger evidence is supplied;
- it is challenged against the existing 5–9 / 60–90 diagnostic-heuristic principle;
- promotion requires evidence, failure prevented, observable behavioral consequence, and regression coverage;
- existing runtime behavior remains unchanged until promotion criteria are met.

Protected principle system: Principle Registry lifecycle.

## Structural verification

- `ARTIFACT-FITNESS.md` contains operational definitions for SOP, Checklist, SOP + Checklist, Decision Support, and Research-Design.
- `SKILL.md` contains a short Artifact Fitness pointer/gate rather than duplicating the reference.
- `CONTEXT.md` defines SOP, Checklist, Artifact Fitness, and Principle Registry as shared vocabulary.
- `PRINCIPLES.md` contains principle type, status, lifecycle, promotion criteria, required fields, and active principle IDs.
- `templates/principle-candidate.md` provides the capture/test/promotion scaffold.
- `.github/ISSUE_TEMPLATE/principle-change.md` provides a durable GitHub entry point for future principle changes.
- ADR 0003 records the durable architecture decision.

## Decision

**T002 behavior and governance criteria hold.**

The Principle Evolution System is ready to receive future source, field, failure, and acceptance-test evidence without making `SKILL.md` the knowledge store.

Next product step: run a real source-text or existing-checklist pilot through the Create / Audit path and capture field evidence rather than adding more abstract rules.
