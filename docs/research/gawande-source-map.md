# Gawande source map

Primary source used for the domain model:

Atul Gawande, *The Checklist Manifesto: How to Get Things Right*. Chapter/page references below follow the uploaded edition used when this project was created.

This file is a source map, not a reproduction of the book.

| Project principle | Source location | What the source supports |
|---|---|---|
| Complexity can exceed individual reliable execution | Introduction, around pp. 2–3 | Modern know-how can become too complex for individuals to deliver reliably even when expertise exists. |
| Memory and attention fail on routine essentials | “The Checklist,” around pp. 34–37 | Routine steps are easily missed under distraction; checklists make minimum necessary steps explicit. |
| Checklist is not a full how-to manual | “The Checklist Factory,” around pp. 122–128 | Good checklists are quick, simple supports for skilled professionals; some important but reliably remembered actions are intentionally omitted. |
| Define a pause point | “The Checklist Factory,” around pp. 122–124 | Checklist design begins by specifying when the list is used. |
| Choose READ-DO or DO-CONFIRM | “The Checklist Factory,” around p. 123 | The two modes fit different execution contexts. |
| Focus on “killer items” | “The Checklist Factory,” around p. 123 | Keep the list short by prioritizing dangerous steps that can still be overlooked. |
| 5–9 items is a heuristic, not a law | “The Checklist Factory,” around p. 123 | Some use this range, but context controls the design. |
| 60–90 seconds is an attention warning | “The Checklist Factory,” around p. 123 | Long pause-point lists invite shortcuts and missed steps. |
| Wording should be “simple and exact” | “The Checklist Factory,” around pp. 123–124 | Use familiar professional language and low-clutter presentation. |
| Complex work needs communication checks | “The End of the Master Builder,” around pp. 65–66 | Construction uses a second checklist-like schedule to specify who must talk to whom, when, and about what. |
| Task + communication checks | “The First Try,” around pp. 101–109 | Surgical checklist designs combine known preventive checks with team briefing for the unexpected. |
| First drafts must be field-tested | “The Checklist Factory,” around p. 124; “The Test” | Real-world testing exposes problems the designer cannot predict; revise and retest. |
| Teamwork is part of the mechanism | “The Test,” around p. 157 | Improved communication/teamwork is associated with improved outcomes in the surgical checklist test. |
| Box-ticking is not the goal | “The Hero in the Age of Checklists,” around pp. 159–161 | The deeper target is teamwork and discipline rather than mechanical completion. |

## Project interpretation

The following terms are project-level synthesis rather than named Gawande frameworks:

- `failure-first checklist engineering`;
- the ordered pipeline used by this repo;
- the `output contract`;
- the audit status vocabulary.

They operationalize the source principles without claiming that Gawande presented them as a formal numbered method.
